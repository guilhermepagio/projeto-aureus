## Findings
- **Aggregate Views (Architecture Delta / Pattern Divergence)**: O backend não utiliza uma camada de serviço (Service Layer). Toda a regra de negócio está concentrada nos Controllers. Além disso, as Entidades do domínio (Domain Models) estão sendo expostas diretamente nos endpoints REST, sem o uso de DTOs. O ideal é o uso rigoroso de `records` do Java, garantindo a criação de DTOs granulares e distintos para entrada e saída de dados (ex: `RequestCriarDespesaFixaDTO` e `ResponseCriarDespesaFixaDTO`), não poupando classes para proteger as fronteiras da aplicação. Essa estrutura atual gera acoplamento, compromete a segurança e dificulta a evolução do projeto. **(Fix - Proposto como Action Item)**
- **Aggregate Views (Duplication Map)**: Há um alto grau de duplicação de código entre os componentes do frontend, especificamente entre os modais de formulário (ex: `DespesaVariavelFormModal.tsx` e `ReceitaVariavelFormModal.tsx` compartilham ~163 linhas) e os hooks (ex: `useDespesasFixas.ts` e `useReceitasFixas.ts`). Essa separação inicial facilita a implementação paralela, mas gera débito técnico a longo prazo. **(Defer - Proposto como Action Item futuro)**
- **Diff-Scope (Verification Gap)**: Nenhuma cobertura de testes automatizados (unitários ou E2E) foi adicionada ou expandida para os novos controladores do backend, entidades de domínio ou componentes do frontend desenvolvidos neste épico. **(Defer - Proposto como Action Item)**
- **Spec-to-Implementation**: Todas as restrições declaradas na spec foram atendidas com sucesso, como os cálculos automáticos das parcelas, bloqueio das rotas por integridade referencial (`RequiresDependencies`), filtragem global (`useMonthStore`) e invalidação de cache do react-query.

## Action items
- **(Fix)** Criar uma camada de serviço (Service Layer) no backend para encapsular e remover a regra de negócio dos Controllers. (Owner: Desenvolvedor Backend)
- **(Fix)** Refatorar as APIs REST para utilizar DTOs (Data Transfer Objects), de preferência usando `records` do Java. Deve haver um DTO distinto para entrada e outro para saída (ex: `RequestCriarDespesaFixaDTO` e `ResponseCriarDespesaFixaDTO`), protegendo a aplicação de todos os lados e evitando reaproveitamento indevido que acopla finalidades diferentes. (Owner: Desenvolvedor Backend)
- **(Defer)** Refatorar os componentes de formulários e hooks de Despesas e Receitas (tanto fixas quanto variáveis) para utilizar abstrações comuns, reduzindo duplicação de código. (Owner: Desenvolvedor)
- **(Defer)** Adicionar cobertura de testes unitários para os Domain Models e Controllers desenvolvidos (DespesaFixa, ReceitaFixa, DespesaVariavel, ReceitaVariavel). (Owner: QA)
